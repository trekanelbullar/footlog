# 長くなる壁打ちで消えていく判断根拠を、残す作業までAIに任せることにした

## 「で、なんでその方針にしたの?」に言葉を詰まらせた件

頼まれていたタスクの進捗を上司に報告した時のことです。

```
やったことを話す。
結論を話す。
「で、なんでその方針にしたの?」と聞かれる。
「えっと……」となる。
```

AIと壁打ちしながら仕事を前に進めることばかりを優先していたため、途中で何を検討して、何を捨てて、最終的に何を根拠にその判断をしたか、その都度立ち止まって整理する、ということをしていませんでした。


そのため、いざ進捗を聞かれると、「ここまで進んだ」「今これをやっている」は話せても、「なぜ今それをやっているのか」「決定の背景は何か」という途中の思考過程がすっぽり抜けていました。整理していなかったため、その場で記憶をたどりながら話すしかなく、うまく伝わらないまま、上司の時間を奪ってしまいました。


## 起きていること — AIとの対話は増えたのに、対話の"跡"は埋もれていく

生成AIと一緒に仕事を進めるのが当たり前になっている方も増えてきていると思います。一方で、こんな経験はありませんか。

### 個人の悩み：思考のプロセスがチャットの奥底に埋もれる

- AIと何十往復もやり取りして、思考を進める
- 途中で「A案かB案か」を検討し、AIの提案も参考にしながらどちらかを選ぶ
- 選んだ理由も、捨てた案も、チャットログの奥に埋もれたままになる
- 報告のタイミングで、自分でもう一度掘り起こす羽目になる
- 掘り起こそうにも会話が長すぎて読み返せず、AIに要約させても「大事なところが漏れていないか」不安になる

AIの普及で、思考の速度自体は上がっているはずです。しかし、そのプロセスを他人に説明できる形で残す作業はどんどん後回しになり、「後でまとめよう」と思っているうちに、何を検討したか自分でも忘れ、埋もれてしまうということ、、


### 報告を受ける側の悩み：結論しか見えず、判断の妥当性が分からない

- 報告のたびに、部下が過去のやり取りを掘り起こす時間が発生する
- 上司は「結論」しか受け取れず、判断の妥当性を検証できない
- AIの提案をそのまま採用したのか、人が検証したのかが分からない

都度記録を残せば解決するのは分かっているものの、できれば「仕事を前に進めること」に時間を割きたい。でも、残さないと後で必ず後悔する——。このジレンマをなんとかしたいと思いました。

## 作ったもの — 残しておくべき"思考の痕跡"を、AIが勝手に拾って資料化する仕組み

作ったのは、プロジェクトを立ち上げて、そこにファイル(AIとのやり取り、メモ、資料など)を置いておくだけのツールです。

プロジェクト内にファイルが格納されると、AIがその中身を時系列も加味しながら読み解き、「何を決めたか」「その理由は何か」「進捗はどうか」「決定に至るまでの流れ」をまとめた資料を作ってくれます。

その後もAIが定期的にプロジェクト内をチェックし、「進捗があった」と判断したタイミングで、また新しくまとめ資料を作り直します。

ポイントは、利用者が新しく何かを書く必要がないことです。普段通りAIとやり取りしたログや、作業中に取ったメモを、そのままプロジェクトに置いておくだけで、あとはAI側が「これは決定事項」「これは却下案」「これはまだ未解決」と仕分けて、資料として組み立ててくれます。


## こだわったポイント — 思考の跡を、掘り返さなくても辿れる形で残す

ただAIにログを渡して「まとめて」と指示するだけなら、既存のツールで十分だと思います。ですがそれらは、結論と元の発言が紐づいていません。後になって「なんでその判断にしたのか」と思考の過程を深掘りしたくなっても、その頃には自分でも忘れていて、要約にはその跡が残っていない。結局、長い会話ログを一から掘り返すしかなくなるのです。

なので、以下の点にはこだわりました。

- 資料中の主張には、根拠になった元テキストの箇所を機械的に紐づける(AIに引用文そのものを書かせず、番号だけを返させて、原文はシステム側が引く)
- 「決定/却下案/未解決」などの記録は追記だけで積み上がっていく形にし、前回の資料に含まれていた誤りを次の資料が引き継がない構造にする
- AIの提案をそのまま採用したのか、人が確認した上で採用したのかを区別して表示する
- 決定・却下案・未解決・わかったことを、形と色で区別したタイムライン図として自動生成する。項目をクリックすると根拠の原文が表示されるので、「今どこまで進んでいるか」を図から一目で追える

「AIが要約してくれた簡潔な文章」ではなく、「後から突っ込まれても耐えられる、根拠つきの記録」を目指しました。

## 「セキュリティは大丈夫なの?」への答え

社内のやり取りやメモをAIに渡す以上、避けて通れない話です。結論から言うと、「AIに見せたくない情報」や「管理者しか見てはいけない情報」を、仕組みとして切り分けています。

- ソースごとに、AIの目に触れさせない除外設定ができます。除外されたものはAIに入力する対象から外れるため、外部(AI)に情報が渡る心配がありません
- 管理者しか知るべきでない内容が含まれる時は、全員向けの資料と管理者向けの資料を別々に作っておき、一般の立場の人には管理者向けの資料のデータ自体を渡しません
- データベースはSupabaseのRLS(行単位のアクセス制御)を有効にしています。仮にアプリ側の実装にミスがあっても、権限のない人はデータベースから直接データを読み出せません
- ユーザーが貼り付けた会話やファイルの内容は、AIへの「指示」ではなく「読むだけの材料」として扱います。そのため、貼り付けた文章の中に指示めいた一文が紛れていても、AIがそれに従って資料の内容を書き換えることはありません
- APIキーらしき文字列は、AIに送る前に伏せ字にしてから保存します。そもそもAIに送られないため、AI経由で漏れる心配がありません

## 技術の話 — 資料ができるまでの4ステップ
![actual_pipeline_diagram.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/4505493/b24cb39d-e738-482c-8bbd-6629307b5d2e.png)

1. 入力：フォルダ直下のファイルを拡張子を問わず全部読み込み、それぞれ別々のソースとしてAIに渡します。
2. 進捗判定：LLMを1回呼び出し、「意味のある進捗があったか」をtrue/falseで判定させます。進捗なしと判定されたら、ここで終了です。無駄に資料を作り直しません。
3. 資料の生成：進捗ありと判定されたケースだけ、別のLLM呼び出しで本文・根拠一覧・タイムライン図（Mermaid）をまとめて生成させます。脚注1つ1つに、根拠になった原文の引用を対応づけて出力させるところがポイントです。
4. 機械的な検証：生成された内容を、今度はLLMを使わずにチェックします。必要な見出しが揃っているか、脚注番号と根拠一覧の対応が取れているか、引用文が実際にその原文中に存在するか（他のソースの文章が紛れ込んでいないか）、タイムライン図が正しい形式になっているか、を確認します。
ダブルチェック：さらに別モデルに、4つの観点（決定が具体的か／理由があるか／ボツ案の明記／作業日記になっていないか）で資料を採点させます。不合格なら指摘を添えて1回だけ作り直し、再度採点。それでも通らなければ「要確認」のフラグを立てて確定させます。

「AIが要約してくれた簡潔な文章」ではなく、「後から突っ込まれても耐えられる、根拠つきの記録」を目指した結果が、このステップ構成です。
