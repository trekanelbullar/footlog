# セットアップ・立ち上げ手順書

対象読者：詳細設計書・PoC仕様書をもとにコーディングAIでコードを生成した後、実際にプロジェクトを動かす人。

**設計変更のお知らせ**：本システムはGoogle Drive・Google OAuth・ブラウザ拡張に依存しない自己完結型Webアプリに設計変更された（設計書第2・8章）。これにより、以前懸念していたセットアップの重さ（OAuth審査、共有ドライブ運用、拡張機能配布）はほぼ解消されている。以前あった「5分版クイックスタート」との差は、以下のインフラ選択（SQLite vs Supabase）だけになった。

## 0. 全体の流れ

1. アカウント・認証情報の準備（人手作業、第1章）
2. PoCでプロンプトを確定する（第2章）
3. コーディングAIに設計書＋確定プロンプトを渡してコード生成
4. 最低限のUI方針を決めて着手する（第3章）
5. 実データでの通し確認（第4章）

この順番が重要。特に2→3の順序を逆にする（プロンプト未確定のままコード生成する）と、後で一番手戻りが大きい部分（LLM呼び出し部分）を丸ごと書き直すことになる。

## 1. アカウント・認証情報の準備（人手作業）

コーディングAIには代行できない、ブラウザ上での手作業。目安時間は初めて行う場合の想定。

| 項目 | 手順概要 | 目安時間 |
|---|---|---|
| Google Cloudプロジェクト作成 | console.cloud.google.comで新規プロジェクトを作成（Cloud Run・Cloud Scheduler・Cloud Storage・Secret Managerを使うため） | 5分 |
| Cloud Storageバケット作成 | プロジェクトファイルの格納先として非公開バケットを1つ作成する（第9.4節） | 5分 |
| Supabaseプロジェクト作成 | supabase.comでプロジェクトを作成し、接続文字列（DB URL）とAPIキーを控える | 10分 |
| Supabase Authの有効化 | 同じSupabaseプロジェクト内でAuth機能を有効化し、メール/パスワード認証を設定する（Google Workspaceを使っている場合はGoogleログインプロバイダも追加できるが、必須ではない） | 5分 |
| Resendアカウント作成 | resend.comでアカウント作成、APIキーを取得。テスト送信だけなら独自ドメイン検証は不要な場合が多いが、送信先アドレスの制限（テストモードでは自分のメールにしか送れない等）を確認する | 10分 |
| OrcaRouter APIキー | 既にコード側で接続確認済みとのことなので、既存のキーをそのまま使う | - |
| Secret Managerへの登録 | 上記すべてのキー・接続情報をGoogle Cloud Secret Managerに登録する（第9.3節、コードに直書きしない）。あわせて`DAILY_COST_LIMIT_USD`（第4.6節のコスト上限）と`SYSTEM_ALERT_EMAIL`（上限超過時・障害時の通知先）を環境変数として設定する | 15分 |
| Cloud Runデプロイ用の権限設定 | デプロイに使うサービスアカウントに、Secret Manager・Cloud Run管理者・Cloud Storage閲覧者/オブジェクト作成者等の権限を付与 | 10分 |

以前あったGoogle OAuth同意画面の設定・共有ドライブの作成は、自己完結型アーキテクチャへの変更により**不要になった**。

**テスト用アカウントの用意について**：Supabase Auth（メール/パスワード）でのログインなので、実在するメールアドレスであれば何でもよい（会社のドメインである必要もない）。デモ用に管理者役・メンバー役の2〜3個のアカウントを作成しておく。

**ここまでで概ね30〜40分**（旧設計の1〜1.5時間から大幅短縮）。Day1の作業に組み込む（設計書第11.4節）。

### ローカル完結の簡易版（すぐに中身だけ触ってみたい場合）
アカウント準備を待たずに、パイプラインのロジックだけ先に確認したい場合は、DBをローカルのSQLiteファイル1つに、ファイル置き場をローカルの適当なフォルダ（PoCで使った`info/`等）に差し替えても動く。この場合、Supabase・Cloud Storageの準備は不要で、OrcaRouterのAPIキーとResendのAPIキーだけで動かせる。バッチ処理をクラウド（Cloud Run/Cloud Scheduler）で自動実行したくなった時点、または複数人でデモしたくなった時点で、上表の本番セットアップに切り替える。

## 2. プロンプトの確定

- PoC仕様書の`results/poc_report.md`を先に完成させる
- Stage2・Stage3・Stage3.5それぞれのプロンプト文言を、PoCで実際に良い結果が出た版に確定し、`prompts/stage2.txt`のように独立したファイルとして保存しておく
- コーディングAIに設計書を渡す際は、この確定済みプロンプトのファイルも一緒に渡す。「設計書の方針からAIに推測させて書かせる」のではなく、「検証済みの文言をそのまま埋め込ませる」形にすることで、精度のブレを避ける

## 3. 最低限のUI方針（ハッカソン向け）

- ゼロからデザインしない。shadcn/uiやTailwind CSSなど、既製のコンポーネント・スタイルをそのまま使う
- **こだわって作り込むのはレポート閲覧画面とMermaid図の2箇所だけ**（デモで実際に見せる部分、設計書第11.1節のMust）
- ログイン画面・プロジェクト管理画面・メンバー招待画面・ファイルアップロード画面などは、ライブラリのデフォルトの見た目のままで良いと割り切る。時間を使うべきところに使う

## 4. 実データでの通し確認チェックリスト

デモ本番の前に、必ず一度最初から最後まで通しで動かす。

- [ ] 管理者役・メンバー役、合わせて2〜3個のテスト用アカウント（Supabase Auth）を用意する
- [ ] 管理者役でログインし、プロジェクトを新規作成する（`goal_description`を入力）
- [ ] メンバー役をプロジェクトに招待する
- [ ] メンバー役のアカウントで、アプリ内の「＋情報を追加」からテスト用ファイル（Excel・コード等）をアップロード、または会話ログを貼り付ける（設計書第8.2節）
- [ ] 監視バッチを手動トリガー（またはデモ用の短縮間隔で自動実行）し、レポートが生成されることを確認する
- [ ] 生成されたレポートに、決定事項・理由・ボツ案が具体的に書かれているか（第5.2節の固定見出し）を確認する
- [ ] 進捗通知メールが実際に届くことを確認する
- [ ] 可視性を「管理者のみ」に設定した情報を1件登録し、管理者役・メンバー役それぞれでWebアプリを開いて見え方の違いを確認する（第5.3節）
- [ ] しきい値を短く設定したテストプロジェクトで、無進捗アラートが実際に届くことを確認する
- [ ] 上記すべてがうまくいかなかった場合の「代替デモ手順」（事前に生成しておいたレポートを見せる等）を1つ用意しておく

## 5. 将来、ブラウザ拡張を追加する場合の注意（任意・現時点では不要）

設計書第8.3節の通り、現行MVPではブラウザ拡張は不要（アプリ内蔵の貼り付け機能で完結する）。もし将来、ChatGPT・Claude.ai等からのワンクリック自動キャプチャを追加したくなった場合は、以下の手順で実機を見ながらDOMセレクタを調べる。

1. 対象サイトを開き、実際に何往復かした会話を表示する
2. 会話の1メッセージ部分を右クリック →「検証」（ブラウザの開発者ツールを開く）
3. そのメッセージ全体を囲んでいる要素のクラス名・属性をメモする
4. 「ユーザーの発言」と「AIの発言」を区別できる属性を見つける
5. 見つけたセレクタを拡張のcontent scriptに書き込み、第8.2節と同じ登録APIを呼ぶようにする

**注意点**：これらのサイトはUIを予告なく変更することがあり、セレクタが変わると拡張が動かなくなる。手動貼り付け機能（第8.2節）は常にフォールバックとして機能し続けるため、拡張が壊れてもサービス自体は止まらない。
