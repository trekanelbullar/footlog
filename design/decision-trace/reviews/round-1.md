### 指摘

- [C-1] 種別: 設計 / 深刻度: high
  - 指摘: 管理者向けの組で出た出来事について、エージェントが member に質問を送ると、質問文・`related_event_summary`（W22）・メール・アプリ内通知のタイトルを通じて、ほかの管理者限定ソースの内容が member に届く。§5.3 (7) の「質問が漏れない理由」はこの経路を塞いでいない。
  - 破綻シナリオ:
    1. manager M が `managers_only` の会話 S2（「A社との契約は来期で打ち切る」）を登録し、実行する。管理者向けの組の出来事 E5 ができる。
    2. member X が `managers_only` を選んで、自分の会話 S4（「A社向け機能は保留にする」理由なし）を登録する（§1.3 の表で member も選べる）。
    3. 次の実行の管理者向けの組の抽出には、S4 の区切りに加えて「すべての今も有効な出来事の要約」（E5 を含む。§5.3 (2)）が入る。LLM は E9「A社との契約打ち切りに合わせ、A社向け機能を保留」を作り、`segment_ids=[S4-1]` を返す。番号の検査は通る（S4-1 はこの呼び出しに渡した番号）。
    4. E9 の決定には理由が無いので、エージェントが起動する。宛先は「根拠のソースを登録した人」＝X（member）。`search_events` は all に絞られる（§5.3 (7) 最終行）が、E9 の要約そのものに E5 の内容がすでに入っている。質問文も E9 の要約から作られる。
    5. X には、「A社との契約打ち切りに合わせて…の理由は？」というメールと、W22 の `related_event_summary` が届く。I1 の「通知メールのどこにも現れない」が破れ、C4 の「メールのどこにも見えない」も満たせない。
    - 同じ経路はもう1つある。根拠が複数のソースにまたがる出来事（`segment_ids=[S2-3, S4-1]`）では、宛先の決め方（「根拠のソースを登録した人」）が1人に決まらない。実装が S4 の登録者 X を選ぶと、`read_segments` で読んだ S2（M のソース）の原文が質問文に入りうる。
  - 提案: 管理者向けの組で起きた質問は、宛先を manager に限る（登録者が member なら質問しない。レポートには「理由は未確認」と出す）。組と関係なく守るなら、「質問文・`related_event_summary` を、宛先が閲覧できるものだけから作れるときに限り送る」という条件をコードで検査する。例えば、出来事の根拠のソースがすべて宛先本人の登録で、しかも抽出の入力に他人の管理者限定の要約が入っていない場合だけ送る。`test_i1_mail.py` に質問メールの経路を足す。

- [C-2] 種別: 設計 / 深刻度: high
  - 指摘: 後から可視性・除外が変わったときの守り（§5.5）が、「引用された」区切り（`cited_segment_ids`）だけを見て版を `withheld` にするかを決めている。一方で LLM は、その版の入力の出来事をすべて見ている。さらに、LLM の入力を組ごとに絞るときに使う列（`visibility_at_creation` / `partition` / 実効の可視性）が、§5.3 の (2)(3)(7) では決まっていない。
  - 破綻シナリオ:
    - (a) 引用されていない内容: 全員向けの v3 の入力に出来事 E7（根拠 S6、`all`）が入っている。組み立ての LLM は「現在地」の文に E7 の内容を混ぜるが、`event_nos` には E8 だけを付ける（あるいは番号を付けず、機械の検査で「根拠なし」になる）。このとき、`cited_segment_ids` に S6 の区切りは入らない。あとで manager が S6 を `managers_only` に変えても、v3 は `withheld` にならず、member は E7 の内容を読める。図も同じで、`mermaid.py` は「その版に入った出来事」から作るので、ノードの `node_evidence` の区切りが `cited_segment_ids` に入るかどうかが決まっていない。入らなければ、ノードのラベル（要約30文字）が残る。
    - (b) 絞り込みの列の取り違え: (2)(3) の「組の可視性で絞った今も有効な出来事の要約」と、(7) の `search_events` の「同じ組で見える出来事」を、`visibility_at_creation` や `events.partition` で実装したとする。S6 が後から `managers_only` になっても、E7 は `all` の組の抽出と `search_events` の入力に入り続ける。新しい出来事 F の要約に E7 の内容が写り、F の根拠は `all` の区切りなので、F の実効の可視性は `all` になる。こうして、その後のメンバー向けの版にずっと載り続ける。
    - (c) 回答ソースの可視性（§5.4）は「質問が出た組」で固定される。質問の後、回答の前に、元の出来事のソースが `managers_only` に変わった場合、回答（非公開になった話題の続き）が `all` として取り込まれる。
  - 提案: (1) `reports` に「入力に渡した出来事の根拠の区切りすべて」（`input_segment_ids`）を保存し、`withheld` の判定はこちらで行う。`cited_segment_ids` は脚注用に限る。(2) LLM の入力に入れる出来事を選ぶ所（(2)(3)(5)(7)(9)(10)）は、すべて §5.5 の実効の可視性で絞る、と明記する。`partition` と `visibility_at_creation` は記録用であって、フィルタに使わないと書く。(3) 回答ソースの可視性は、回答した時点での元の出来事の実効の可視性から決める。(4) 前提の確認: (b) の写り込みは、F を作った時点では正当だった情報の再分類である。I1 をさかのぼって適用するのか（写り込みまで追うのか）を spec で決めてほしい。追わないなら、§5.5 の「穴ふさぎ」という書き方を弱め、§12 の残るリスクに移す。

- [C-3] 種別: 設計 / 深刻度: high
  - 指摘: 同じファイル名で再アップロードすると、既存ソースの新しい版になる（B2）。しかし、別の人のソースや `managers_only` のソースに対して再アップロードしたときの権限と、`visibility` の入力の扱いが決まっていない。どちらに実装しても、I1 か I3 のどちらかが破れる。
  - 破綻シナリオ:
    - (a) W9 の `visibility` をソースに反映する実装: manager M が `budget.xlsx` を `managers_only`（S5）で登録し、実行して管理者向けの出来事 E3 ができる。member A が `budget.xlsx` という名前の別のファイルを `visibility=all` で W9 に送る。`unique(project_id, filename)` で S5 の v2 になり、S5 の可視性は `all` になる。この変更は W11 を通らないので、`source_audit_log` に残らない（H2・I3 の「履歴」が欠ける）。W11 の「member は `managers_only`→`all` にできない」という規則もすり抜ける。次の実行では、E3 の実効の可視性が（S5 の今の状態から）`all` になり、全員向けの版の本文・図に E3 が載る。脚注には v1 の区切りの原文が出る（§5.6 は `source_segments.text` を引く）。
    - (b) 反映しない実装: A のファイルは、A が見られない `managers_only` のソース S5 の現在の版になる。A は W10 で自分の登録を見られない（`uploaded_by` は M のまま）。M のソースの現在の版は、A の中身に置き換わる。W9 の応答の `version_no: 2` から、A は同じ名前の非公開ファイルがあることを知る。
  - 提案: 再アップロードで既存ソースに版を足せるのは、元の登録者か manager に限る。それ以外は 409 `filename_taken` を返す。再アップロードでは `visibility` の入力を無視し、可視性を変えられるのは W11 だけにする。この2点を §2.2 と §1.3 の表に書き、`test_i1_view.py` に「別の人が同じ名前で再アップロード」のケースを足す。

- [C-4] 種別: 設計 / 深刻度: mid
  - 指摘: §1.3 の権限表では、manager の判断を member が取り消せる。また、manager が1人もいない状態になりうる。
  - 破綻シナリオ:
    - (a) manager M が、member A の登録した会話 S8 を「機密（confidential）」として除外する。表の「除外する／除外を戻す：自分が登録したソースのみ」によって、A は W12 で除外を戻せる。S8 は次の実行で LLM の入力に戻り（C5 の対象外になる）、`all` であれば全員向けの版と進捗メールに載る。
    - (b) プロジェクトで唯一の manager が、W7 で自分のロールを `member` にする（`role` の変更は manager に許されていて、自分自身を除く制約が無い）。するとプロジェクトに manager がいなくなり、W3 の `excluded_summary` も管理者向けの版も、誰にも見えない。I5（除外は件数として必ず管理者に見える）が破れる。設定の変更やメンバーの追加も、二度とできなくなる。
  - 提案: 除外を戻すのは、「除外した人が本人で、しかも最後の除外の操作が本人によるもの」の場合だけに限る（`source_audit_log` の最後の行で判定する）。それ以外は manager だけにする。`managers_only`→`all` と同じ非対称の扱いにする。W7 は、最後の manager を降格する変更を 409 で拒否する。

- [C-5] 種別: 設計 / 深刻度: mid
  - 指摘: 管理者向けの組の抽出では、`supersedes_event_no` に全員向けの出来事の番号も選べる（§5.3 (4)「その組で見えている出来事」）。一方、「今も有効」の定義（§5.3 (9)）は、置き換えた側の出来事の可視性を見ていない。そのため、管理者限定の出来事が全員向けの決定を置き換えると、メンバー向けの版からその決定が黙って消える。
  - 破綻シナリオ: 全員向けの出来事 E2「リリースは10月」がある。manager が `managers_only` の会話で「リリースは12月に延期（非公表）」を登録する。管理者向けの組の抽出が、E11（`supersedes_event_no=2`）を返し、番号の検査も通る。次の全員向けの版では、E2 が「置き換えられた」ので入力から外れ、E11 は `managers_only` なので入らない。member の「現在地」からリリースの時期が消え、しかも理由は示されない。版の差分から「非公開の変更があった」ことが推測できる（間接的な I1 の漏れ）。全員向けの組の次の抽出も、E2 を文脈として見られなくなり、同じ決定を重複して作るおそれがある。
  - 提案: 「今も有効」を閲覧の単位ごとに決める。全員向けの版と全員向けの組の文脈では、「実効の可視性が `all` の出来事による置き換え」だけを置き換えとして扱う。あるいは、管理者向けの組の `supersedes_event_no` は `managers_only` の出来事に限る。

### 補足（指摘枠外・確認済みで問題なしとしたもの）
- W17 は `X-Cron-Secret` だけ、ユーザー用は JWT 必須で、互いに受け付けない（§1.2）。W24 はデータを返さない。本人をなりすます欄が無く、`sub` を JWT から取るので、共有シークレットだけで別人になることはできない。
- W11〜W13・W15・W16・W21〜W23 のパスには pid が無い。worker が sid・rid・nid・qid から project_id か宛先を引いて所属を確かめる必要がある。§1.3 の「全APIがここを通る」で意図は読み取れるが、実装時に `authz.py` の入口で「リソース→project_id の解決」を必須にしておくとよい（指摘には上げない）。
- I2（表示のたびに原文を引き、テキストノードで出す）、I4（入力に渡した番号との照合）、I7（唯一の入口と、単価不明のモデルの拒否）は、構造として成り立っている。
