- U6：取り込みは W8・W9 の中で同期的に行う
- U7：web が W15 を最大300秒待ち、画面は W16 を2秒ごとに問い合わせる。worker は240秒で打ち切る
- U8：図の文法は作りとテストで保証し、描けなければブラウザ側で箇条書きに切り替える
- U9：design.md §1.3 の権限表のとおり
- U10：プロジェクトごとに member と manager の2つ。admin は作らない

- U12：段階ごとの出力上限は環境変数で設定。既定は抽出・組み立てが4000、それ以外が500

## AD-2 思考モードと出力上限（2026-09-21）

- 思考モードの既定は、全段階 `off`。
- ある段階で思考モードが `off` 以外のときは、思考に使われる分で出力の枠が食われる（PoC で `orcarouter/auto` が出力上限を使い切り、本文が空になったのと同じ事故）。そこで：
  - その段階の出力上限が `ORCAROUTER_REASONING_MIN_MAX_TOKENS`（既定 16000）より小さければ、実際に使う上限をこの値まで引き上げる。
  - 引き上げたときは、起動時に警告を出す（段階名、設定値、実際に使う値）。
  - コストの予約（design.md §6.1）は、引き上げた後の上限で見積もる。

## AD-3 テスト用の DB（2026-09-21）

- DB を使うテストは、手元では Homebrew の PostgreSQL 16 に作った `decision_trace_test` で流す（`TEST_DATABASE_URL=postgresql://localhost/decision_trace_test`）。
- `.env` の `DATABASE_URL`（Supabase）は、テストでは**絶対に使わない**。テストの接続先は `TEST_DATABASE_URL` だけから取り、ホスト名が `localhost`・`127.0.0.1`・`postgres`（CI のサービスコンテナ）のどれかでなければ、テストを始めずに失敗させる。
- CI のサービスコンテナも、手元と同じ PostgreSQL 16 にする。

## AD-4 app_worker の RLS の扱い：ポリシー方式（2026-09-21、ユーザー決定。当初の BYPASSRLS 案は取り消し）

- 全表で RLS を有効にする（design.md §3）。そのうえで、各表に `app_worker` にだけ全行を許すポリシーを作る：`CREATE POLICY app_worker_all ON <表> TO app_worker USING (true) WITH CHECK (true)`。`anon`・`authenticated` 向けのポリシーは作らないので、Supabase の匿名キーとログインユーザーのキーからは引き続き何も読めない。
- `app_worker` に BYPASSRLS は**付けない**。理由：PostgreSQL 16 以降は BYPASSRLS つきのロールを作る側も BYPASSRLS を持っている必要があり、スーパーユーザーではない Supabase の `postgres` ユーザーで作れるかが不確か。ポリシー方式なら特別な権限が要らず、手元と Supabase で同じように動く。
- ポリシーは、どの操作に効くかを1つのポリシー（`FOR ALL`）で決める。追記専用の表の UPDATE・DELETE・TRUNCATE は、ポリシーではなく、トリガーと REVOKE で止める（design.md §3.2 のまま）。
- 表を足すマイグレーションでは、その表にも同じポリシーを必ず作る。
- 起動時の確認（AD-5）では、`app_worker` が BYPASSRLS を持っていないことも確かめる。

## AD-5 起動時の接続ユーザーの確認と、マイグレーション用の接続の分離（2026-09-21）

- worker は起動時に、今つないでいる DB のユーザーを確かめる。`current_user` が `app_worker` でない、またはスーパーユーザーである場合は、起動しない（管理者の接続文字列で誤って起動したことに気づくため）。
- テスト環境だけは除く。`APP_ENV=test` のときだけ確認を飛ばし、それ以外（未設定を含む）は必ず確認する（設定を忘れたときに、確認が働く側に倒す）。
- マイグレーションは `MIGRATION_DATABASE_URL`（Supabase の `postgres` ユーザー）で流し、アプリの `DATABASE_URL`（`app_worker`）とは分ける。マイグレーションのコマンドは `DATABASE_URL` を読まない。

## AD-6 qwen の思考モードを止める指定（2026-09-21、手元での確認中に判明）

- `qwen/qwen3.7-flash` は、既定で思考モードが動く。こちらが何も送らない（設計書 §6.2 の `off`）と、短い入力でも1,000トークン以上を思考に使い、抽出1回が30秒のタイムアウトを超えて失敗した。
- ゲートウェイ経由で試した指定のうち、思考が止まったのは `enable_thinking: false`（リクエストの本文に追加）だけだった（0.9秒、思考のトークン0）。`reasoning_effort: low`・`reasoning.enabled=false`・`reasoning.effort=none` では止まらなかった。
- そこで、段階の思考モードが `off` で、モデル名が `qwen/` で始まるときだけ、`enable_thinking: false` を送る。`off` 以外のときは、これまでどおり `reasoning_effort` を送る。qwen 以外のモデルには送らない（受け付けずにエラーになるおそれがあるため）。

## AD-7 手動実行では Judge のやり直しを省く（2026-09-22、ユーザー決定）

- 手元での確認で、C1（貼り付けてから30秒以内）が通らなかった（4回で16・32・46・52秒）。抽出が11〜21秒とばらつき、Judge が1回目で不合格になると、組み立てのやり直しで8〜18秒が足されるため。
- そこで、手動実行（`trigger = manual`）では、Judge が不合格でも組み立てをやり直さず、`judge_status = flagged`（画面に「要確認」）で保存する。定期実行（`trigger = schedule`）では、これまでどおり1回だけやり直す（spec F4）。
- spec F4「不合格なら最大1回だけ再生成」を、手動実行でだけ「0回」にする変更。機械の検査（番号の実在・根拠なしの印）は、手動実行でも必ずかける。

以下 AD-8〜AD-12 は、相方からの改善提案（2026-09-22、ユーザー経由）。実装は AD-8 から順に。各項目にテストを付ける。

## AD-8（AD-a）貼り付けの案内

- web：貼り付けの入力欄の近くに、常に「会話をそのまま貼ると、AIの提案かどうかの印がより正確になります」と表示する。
- worker：W8（会話の貼り付け）の応答に `speaker_counts: {"user": n, "ai": n, "unknown": n}` を足す。
- web：`speaker_counts` の user と ai がどちらも0（すべて unknown）なら、貼り付けの直後に「話者の目印が見つからなかったため、出どころの印は付きません」と表示する。

## AD-9（AD-b）予算切れと無進捗の区別

- worker：日次のコスト上限に達して分析を行わなかった日（`daily_cost_alerts` に行がある日、日本時間）は、無進捗の判定の経過時間から除く（その間は無進捗アラートを出さない）。土日を除く計算と同じ扱いで日を除外する。
- worker：実行が `cost_limited` で終わった日は、そのプロジェクトの manager に、アプリ内通知（kind = `cost_limited`、タイトル「本日は費用の上限に達したため、分析を行っていません」）を、プロジェクトごとに1日1回だけ送る。メールは送らない（SYSTEM_ALERT_EMAIL への通知は従来どおり）。
- worker：W3（プロジェクト）の応答に `cost_limited_today: bool` を足す（日本時間の今日の `daily_cost_alerts` に行があれば true。全員に返してよい）。
- web：`cost_limited_today` が true なら、プロジェクトの画面とレポートの画面の上部に「本日は費用の上限に達したため、分析を行っていません」と表示する。アプリ内通知の一覧にも出る（kind の表示名を足す）。

## AD-10（AD-c）却下案の再浮上の検知

- worker：抽出の入力の「今も有効な出来事」に加えて、同じ組で見える**過去の `rejected_option`**（置き換えられたものも含む。除外は除く）を渡す。エージェントの `search_events` の対象にも含める。
- 抽出の出力に、出来事ごとの任意の項目 `similar_rejected_event_no`（整数か null）を足す（契約の型に任意の項目として追加。既存の呼び方は変わらない）。コードの検査で、その番号が「その呼び出しに渡した過去の却下案の番号」でなければ null にする（組をまたいだ示唆を防ぐ。不変条件 I1）。
- 対象は `decision` / `finding` / `open_issue` の出来事だけ。`events` に列 `similar_rejected_event_no`（追記時に書く、以後変えない）を足す（マイグレーション 0002）。
- 版の組み立て：その版の入力に、該当の却下案（実効の可視性がその版で見えるもの）があるときだけ警告を出す。見えなければ警告を付けない（全員向けの版で管理者限定の却下案との類似を示唆しない）。
- W19 の `flags` に `rejected_similarity: [{"event_no": n, "rejected_event_no": m}]` を足し、`node_evidence` に却下案 `E{m}` の根拠の原文も入れる（web はリンクから原文を開ける）。本文の該当の文に「〔過去に却下した案と類似：E{m}〕」をコードで付け、レポートの冒頭に警告の件数を出す（未確認の件数と同じ形）。

## AD-11（AD-d）質問の上限

- 1人あたり、日本時間の1日に届く質問は最大3問まで（全プロジェクト合計）。1回の実行で最大2問（D10）はそのまま。
- 超えた分は `agent_questions.status = 'deferred'` で保存し、メールもアプリ内通知も送らない。定期実行（W17）の最初に、その日の枠が空いている deferred の質問を古い順に送り、`open` にする（送る直前の可視性・ロールの再確認【C-1・B-X2】は従来どおり）。
- `agent_questions.status` に `deferred` を足す（マイグレーション 0002）。

## AD-12（AD-e）出来事の検索

- worker：W25 `GET /internal/projects/{pid}/events/search?q=<文字列>`（web（ユーザー）、所属者）。出来事の要約と理由の部分一致（大文字小文字を区別しない、2文字以上、最大50件、新しい順）。
- 出力：`[{"event_no", "kind", "occurred_at", "summary", "reason", "evidence": [{"label", "text"}]}]`。`evidence` は根拠の区切りの原文（表示のたびに DB から引く、I2）。
- 閲覧者のロールで見える出来事だけに絞る：member は実効の可視性が `all` の出来事だけ、manager は除外以外。置き換えられた出来事も対象（過去の経緯を探すため）。既存の権限の確認（所属・親子を1つの条件で引く、404）を必ず通す。
- 生の会話ログ（source_segments の本文）は検索の対象にしない（出来事の要約と理由だけを検索し、原文は結果の表示にだけ使う）。
- web：レポートの画面に検索窓を置き、結果を「種類・日付・要約」の一覧で出す。各結果から根拠の原文を開ける（脚注と同じくテキストノードで出す）。

## AD-14 レポート画面の3カラム化（2026-09-22、相方の設計仕様書 design/ui-spec-3col.md）

web だけの変更（worker・API は変えない）。design.md の画面の章は書き換えず、ここを優先する。

- 骨格：左＝ツリー（264px）、中央＝文書ビュー、右＝根拠パネル（320px）。1024px 未満では、ツリーはハンバーガーで開くドロワー、根拠パネルは脚注を押したときに下から出るシート。
- 階層の読み替え：仕様書の「ワークスペース → プロジェクト → フォルダ → 記録」を、今のデータの「プロジェクト → 版（レポート）」の2階層に当てる。ツリーは プロジェクト名 → 固定見出し「決定ログ」→ 版（新しい順、「v4 / 2026-09-22」）。ワークスペースは表示しない。
- ステータス（チップ）：検査中（実行が running）＝グレー、要確認（Judge が flagged・未確認の出来事が1件以上・誘導の疑いあり）＝オレンジ、検査済み（それ以外）＝グリーン。「承認済み」は今のデータに無いので作らない。NEW 件数＝1つ前の版の時系列に無い出来事の数。
- AI要約ブロック：今のレポート本文（決定・理由・却下案・次にやること・現在地）。ラベルは「AIによる自動生成 — n件の会話ログとm件の資料から」。n・m は、この版の脚注が引いたソースを種類別に数えたもの（会話・回答＝会話ログ、ファイル＝資料）。
- 脚注：本文の番号を押すと、右パネルに引用カード（ソース名・記録日時・原文を一字一句そのまま・話者）を出す。本文はスクロールさせない。
- 原本ソース一覧：project_sources を種別アイコン（会話／PDF／Excel／Word／PowerPoint／テキスト／回答）つきで並べ、押すと「資料」タブの該当行へ。除外の件数と理由の内訳は manager にだけ出す（既存の権限のまま）。
- 根拠パネル上部の検索は出来事の検索（AD-12）。結果を押すと、その出来事の根拠を同じパネルに出す。下部の「この記録について」に、生成元の件数・最終更新・ステータス・版・読者を出す。コストと所要時間は今の API に無いので出さない。
- 残すもの：中央上部の操作帯（＋資料を追加・今すぐ確認）と実行中の進行表示、出どころの印、却下案の再浮上の警告帯（AD-10）、図と描けないときの箇条書き、タブ（レポート／資料／メンバー／質問）。
- 書体は全体サンセリフ（Noto Sans JP）。明朝は使わない。白背景、薄いグレーの境界線、影なし。
